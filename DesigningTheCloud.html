Designing The Cloud


Why is the cloud such a big disruptor in the computing landscape?


On-demand: computing power using remote servers and farms

Elasticity: to scale up and down as according to demand

Multitenancy: many different clients can use the same cloud infrastructure

Cloud infrastructure can also hold virtual networks in our cloud infrastructure as well as virtual servers.


Say we have a large server farm with 100 individual computers with network infrastructure set-up to accomodate this. Switches, routers, redundancy, Next-Generation Fire Walls, ect.


We then migrate this to one very large physical server running 100 virtual servers inside. What then happens to this network and it's infrastructure?


Similarly, we virtualize the network infrastructure as well. This is referred to as:


Network Function Virtualization


So instead of the physical hardware as necessary for this previous 100 computer network, we can run the switches, routers, and all other required networking hardware virtually to perform the same functionality with these 100 virtual servers inside the machine. This can be configured and managed from the Hypervisor.


These have the same functionality as the physical device, but are running entirely within the virtualized network running on this machine. So, routing, switching, load balancing, firewalls, and other functions can be performed in this software only environment.


This, naturally, makes deploying modifications to the network as easy as a push of a button. Additionally, this allows for complex interactions between containers, virtual machines, and access for different clients on on the network.


Virtual Private Cloud (VPC)


This is one very common form of cloud computing seen in commercial and enterprise configurations. It is a pool of resources created in a public cloud, allowing for easy storage and retrieval of files or other data as required.


It's very common in large enterprise scenarios to have many separate VPCs for different application instances or different parts of the company. This allows you to keep these instances separated but still manage all of these virtual appliances.


Though these VPCs are separated, we may need to be able to connect these different VPCs and communicate between them. This is called a Transit Gateway. You can think of this as a router for your cloud.


Virtual Private Network (VPN)


If these VPCs need to connect to networks outside of the enterprise, you may need additional security measures in the form of a VPN connection. In this scenario, you may have someone outside of the network or in a remote location connect in through a VPN tunnel, access the transit gateway and be able to communicate with the VPCs in your cloud.


Though a common use-case for VPNs is for people in remote locations or at a user's workstation to connect to your private cloud features, it may be that you want to make your private cloud instances available to anyone on the internet.


In that scenario, you may want to use a Virtual Private Cloud (VPC) Gateway. This allows users anywhere in the world to have access to the application.


VPC Network Address Translation (NAT) Gateway


This allows your cloud subnets to be able to connect to external sources outside of the network, while retaining the privacy of the VPC. The VPCs and networks inside of the VPCs on our cloud use the VPC NAT to translate to a public IP address to be able to communicate out over the internet.


This includes protocols that allow outbound access from the VPC, but not allow inbound access from external devices.


VPC Endpoint


This provides direct connection between a VPC on one cloud provider, to a VPC on another cloud provider.

Security groups and lists


Additional security on top of the VPCs is often required. This can be achieved through controlling which traffic can and cannot be sent through and from the VPC. This is done through security groups and lists.


Many of these are controlled through port numbers and TCP and UDP protocols.


You may define a TCP or UDP port number (Layer 4) and add this to your inbound or outbound rules in your security groups. Additionally, individual addresses (Layer 3), blocks of addresses using CIDR, or to specify IPv4 or IPv6 ranges within your security.


This acts much like a NG firewall blocklists but for your VPCs.


Network Security List



In your cloud provider's frontend you would include in your security list a list of rules you would like to assign. In the above image example, there is a rule for inbound traffic coming from the subnet under port 443, as well as for port 22.


You may see that the listed IP address is 0.0.0.0/0. This shows that any IP address coming from those port numbers communicates with these rules.


Once you have applied your Network Security List, it'll be applied to all of your VPC networks. In the above example, these lists are being applied to 3 Virtual Cloud Networks with the name Subnet X,Y, and Z.


However, a drawback for the Network Security List is that your rulesets may require more granularity than the blanket rules being applied to all VPC subnets. The ruleset will be applied to all of the subnets under the VPC using the Network Security List.


Network Security Group



This can be done through the Network Security Group. Using this, you may apply security rules to specific Virtual Network Interface Cards (VNIC).


VNICs are the equivalent to the network cards found in physical computing, and having them operate within your VPC can allow similar interactions with your virtual servers as you would with many physical servers under the same network.


These, therefore, can be assigned to specific devices and network connections, allowing much more flexibility than the blanket Network Security List.


In the above image example, Group NSG-A, like the Network Security Group image, is being applied to port 443 with all IP addresses coming through that port communicating with the rule. However, as notated by the green shield, it is only being applied to specific VNICs inside the VPC, even within the same subnet "Subnet X".


If additional security is required, a virtualised firewall may also be recommended.
